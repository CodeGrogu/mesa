Open work after round 2. Numbers match the master list from 2026-11-19. Effort: (S) small, (M) medium, (L) large. Evidence for each item is in [FINDINGS.md](FINDINGS.md), [IMPLEMENTATION.md](IMPLEMENTATION.md), [ROUND2.md](ROUND2.md) and the `sweep/` inventories.

## Implementation: fixes

- [x] **4. VA-API → Vulkan zero-copy (M). Done (2026-11-19).** The `EINVAL` came from FFmpeg, not the drivers. `vaapi_map_from()` routed Vulkan destinations to the memory mapper instead of returning `ENOSYS`. The fix is a patch to libavutil. NV12 and P010 now map byte-exactly through `hwmap`, and 1080p H.264 reaches Vulkan about 3× faster than with a CPU download (1.49 s vs 4.58 s for 960 frames). See [zero-copy/README.md](zero-copy/README.md).
- [x] **18. Iris timers, remaining work (M). Done (2026-11-22).**
  - *Live rollover:* 2,000 back-to-back `GL_TIME_ELAPSED` intervals were queued across the 36-bit wrap. Interval 932 contained it and measured 11.124 ms against an 11.170 ms median. Every GPU-resolved result equalled the client result, and there were no outliers (`evidence/iris-timer-conversion/straddle.log`).
  - *Forced submissions:* timer snapshots now go in whichever batch has pending work. The other batch gets an `order_after` link that `iris_get_command_space()` honours before its next command of any kind: draws, dispatches, clears, blits and copies. A small dispatch inside `GL_TIME_ELAPSED` went from 73.7 to 15.1 µs per iteration (12.2 µs without a query). The ordering, conversion and saturation probes and Rusticl profiling pass (`evidence/iris-timer-placement/`). Rusticl's per-event latency is unchanged within noise, because its event cost is elsewhere.
  - *Xe and blitter:* not applicable here. KBL uses i915, and Iris issues no timer snapshots on the blitter; the Xe sysfs path is shared code.
- [x] **26. ANV error handling (S). Done.**
  - An explicit modifier layout that isl rejects now returns `VK_ERROR_INVALID_DRM_FORMAT_MODIFIER_PLANE_LAYOUT_EXT` (it returned `OUT_OF_DEVICE_MEMORY`). Verified with `small-fixes/modifier-layout.c`: a 1000-byte Y-tiled pitch now gets the specific error, and a 1024-byte pitch still succeeds.
  - Batch clone: a clone failure already frees its partial copy, and the FIXME now says so. The real leak was a `seen_bbos` allocation failure after a successful clone; the copies are now handed to the primary command buffer. Compile-checked only, since that out-of-memory path can't be triggered from a normal test.
- [x] **33. Rusticl clock telemetry (S). Done.** Iris reads the maximum configured frequency from sysfs: `gt_max_freq_mhz` on i915, `tile0/gt0/freq0/max_freq` on Xe. If that fails, it falls back to 400. clinfo now reports 1000 MHz (it reported 400), and the OpenCL profiling test still passes.

## Implementation: new features

- [x] **6 → 11. Vulkan HEVC Main/Main10 decode on Gen9 (L). Done with HuC (2026-11-20).** After a reboot with `i915.enable_guc=2`, HuC 4.0.0 authenticated, and ANV exposes `VK_KHR_video_decode_h265` under `ANV_DEBUG=video-decode`. All 4 clips (192 frames, Main and Main10, I/P/B with multiple GOPs) decode identically to software. No code change was needed. See [hevc-huc/README.md](hevc-huc/README.md).
- [x] **12. Vulkan HEVC encode on Gen9 (L). Dropped 2026-11-22 at the user's request.** HEVC hardware encode already works on this GPU through VA-API (`hevc_vaapi`, iHD `VAProfileHEVCMain/Main10` `EncSlice`). A Vulkan port would drive the same kernel-based encoder, so it could not be faster or better. Use iHD as the reference. Start with fixed-QP Main and Main10. 2026-11-22 finding: KBL HEVC encode in iHD is kernel-based (`codechal_encode_hevc_g9_kbl.cpp` loads `IGCODECKRN_G9`, 0 VDENC references), unlike ANV's Gen9 H.264 encode, which uses VDENC. A port means running iHD's Gen9 ENC kernels from ANV, plus BRC. Months, not a patch.
- [x] **13. H.264/HEVC bitrate control in Vulkan encode (M–L). Done for H.264 (2026-11-22).**
  - *Port:* ANV's HuC BRC now runs on KBL-class Gfx9, using the firmware ABI extracted from iHD.
  - *Results:* across 30 s 1080p streams at 2–8 Mbit/s, with GOP 30–120 and with and without B-frames, 7 of 8 configurations land within 0.2–1.3% of target with no VBV underflow, on par with iHD. CTS: the 4 rc_cbr/rc_vbr cases now pass, with 0 failures.
  - *Limit:* noisy content needing more than QP 51 overshoots (+37% at 2 Mbit/s). iHD handles that case with a conditional re-encode, and Gen9's only conditional batch end aborts the whole command buffer (measured).
  - *HEVC:* there is no HEVC encode on Gen9 (item 12).
  - See [avc-brc-gen9/README.md](avc-brc-gen9/README.md).
- [x] **14. Vulkan Video decode on by default on Gen9 (M). Done (decode).** CTS with no debug flag: dEQP-VK.video.decode h264/h265/vp9 98/98 supported cases pass, 0 failures (the other 98 need `VK_KHR_unified_image_layouts`). H.265 needs HuC, which ANV checks. The drirc option `anv_gfx9_video_decode=false` opts out. Encode stays behind `ANV_DEBUG` until rate control works (item 13); its CTS run was 22/22 supported cases passing.
- [x] **17. Broaden multi-mip HiZ (M–L). Done, except full mip chains.** Multi-LOD HiZ now covers D16, X8_D24, D24S8, D32 and D32S8, including array images. The harness grew 10 new exact per-pixel cases (20.5M checks): other formats, resolves, and layered images with the other layers checked untouched. All 26 cases pass on debug and release, and the 7,771-case depth CTS list is unchanged (0 failures). *Not done:* full mip chains. Their 1×1/2×2 LODs can't meet the 8×4 HiZ-op rule, and ANV tracks aux per image rather than per LOD, so this needs a per-LOD aux redesign, not a gate change. See `evidence/hiz-wide/`.
- [x] **27. `G16B16G16R16_422` / `B16G16R16G16_422` and linear YUV chroma reconstruction (M). Done (2026-11-22).**
  - *16-bit formats:* these are stored as `R16G16_UNORM` at full width. Luma is filtered by the hardware, and a new NIR pass rebuilds chroma on the half-width grid, supporting midpoint/cosited locations and nearest/linear filters.
  - *8-bit linear chroma:* the sampler's own YCRCB filtering failed 20 CTS cases, so the same pass rebuilds linear chroma for the 8-bit packed formats.
  - *CTS:* over 68,414 YCbCr and format-property cases, 796 went from not supported to Pass, with 0 regressions and 0 failures. See [ycbcr-422/README.md](ycbcr-422/README.md).
- [x] **36. Vulkan OA performance counters (M). Done (2026-11-22), and it found an upstream regression.**
  - *Regression:* since upstream `0a51842f7ab` (May 2024), Gfx8–11 OA reports were parsed as the Haswell format, so every OA counter was wrong in Iris, ANV and hasvk. For example, "GPU Busy" read 2,495% and "EU Active" read 0. This is fixed, and checked against known values under temporarily granted access: "CS Threads Dispatched" is exactly 4 per SIMD8 group.
  - *Pipeline statistics:* pipeline-statistics counters are now separate from OA. `VK_KHR_performance_query` works under the default `perf_stream_paranoid=1`, with exact invocation counts.
  - *CTS:* performance_query has 4 pass and 0 fail under both settings (all 12 were not supported at paranoid=1). See [perf-query/README.md](perf-query/README.md).
- [x] **46. Native ASTC 5x5 in Iris (M–L). Done (2026-11-22).** i965's workaround is ported: aux is disabled for every texture sampled together with ASTC 5x5, and a CS stall plus texture invalidate runs on each ASTC↔aux transition in the sampler cache, including BLORP sources. With the workaround compiled out, the GL test hung on its first iteration. With it, 1,200 iterations ran clean, and output matches the software decode within 1/255. `IRIS_GFX9_EMULATE_ASTC_5X5=true` opts out. See [astc5x5-iris/README.md](astc5x5-iris/README.md).
- [x] **47. Software fallbacks for ray tracing, mesh shaders, VRS and sparse textures (L, low value). Closed 2026-11-22.** Ray tracing, mesh shaders and VRS were dropped at the user's request. VRS emulation would only shade at 1x1, so it could never be faster. Sparse is blocked, because Gen9 i915 gives Mesa no way to remap GPU pages (no VM_BIND, no TR-TT).
- [x] **48. Software AV1 decode into presentation (L). Done.** mpv with `hwdec=auto-safe` decodes AV1 in software (dav1d, 6–9× real time at 1080p30, 0 decoder drops) and presents through gpu-next/Vulkan. The same config uses the GPU decoders for H.264 and VP9 (0 drops). Evidence: [av1-playback/](av1-playback/README.md).

- [x] **New (from test 5). Gen9 transfer queue on the copy engine (L). Dropped 2026-11-23 at the user's request: unsafe on this hardware.** Implemented behind `anv_gfx9_copy_queue` (default off) on branch `hd620-gen9-copy-queue-wip`: commits e29fc100b22, 0692a239b4c, effeb160819 and 9f9de36682c. A no-execution dry run (every execbuf intercepted, batches decoded) found and fixed three bugs: sign-extended blitter addresses, the missing companion command pool on Gfx9, and empty secondaries. All 54 transfer-queue CTS cases then dry-run clean. On hardware even `fill_buffer_whole` still wedged bcs0 and then rcs0. Both engine resets timed out and the laptop hard-locked (2026-11-22 22:30 and 23:41, 2026-11-23 00:05). The likely remaining cause is the Gen9 blitter and ANV's high VAs (about 0xeffe_xxxx_xxxx); the probes used about 4 GiB. Further testing needs more hard lockups. Tools: `bcs-queue/` probes, and `~/.local/state/catchingup/bcs-dryrun/` (noexec.so, scan.py). `XY_FAST_COPY_BLT` ran at 10.5 GB/s versus 6.3 GB/s for render-engine copies. ANV has no Gen9 BCS command emission, and every BCS execbuf goes through i915's command parser, which limits batch chaining. Needs a design, plus concurrency, visibility and ownership tests.
- [x] **New (from test 15). VP9 8-bit encode on KBL through iHD (L, out of Mesa). Closed 2026-11-22: blocked in iHD, and the i965 route was dropped by the user.** The legacy i965 driver (`i965-va-driver-shaders`, open-source Gen9 kernels) may offer VP9 encode on KBL. That is untested and not pursued. iHD has the KBL HCP VP9 encode commands, but no Gen9 VP9 encoder and no Gen9 VP9 ENC kernels, and the Gen9 caps never add the entrypoint. Enabling it means writing a new encoder plus EU kernels. [vp9-encode-ihd/](vp9-encode-ihd/README.md). No driver exposes it, even though Intel marketed the hardware feature.

## Performance optimization

Driver flushes and state:
- [x] **19. Opt-in to skip the clear-colour state-cache invalidate (S). Done.** Set the drirc option `anv_gfx9_skip_clear_color_state_invalidate` (off by default) in drirc or the environment. On the release build, the `load` scenario drops from 2.3–2.6 µs to 1.4–1.5 µs per render pass, and every `load`/`blend2` pixel check passes (`gen9-stalls/drirc-option.txt`).
- [x] **20. `MEDIA_VFE_STATE` re-emit after GPGPU → 3D (M). Done: no reproducer, so an opt-in drirc option.**
  - *Search:* 3.7 million compute→3D switches in two pixel-checked patterns, one with the dispatch writing the vertices the draw reads, ran with the re-emit removed and never failed. A negative control fails 413 of 1,024 cells.
  - *Decision:* the re-emit also serves a preemption workaround, so it stays by default. `anv_gfx9_skip_vfe_reemit` skips it, saving about 0.6 µs per switch. See [vfe-flicker/README.md](vfe-flicker/README.md).
- [x] **21. Iris dynamic VAO fast path on KBL (S). Measured; no change.** Measured with glmark2 over 5 rounds. It is correct, but no scene got a measurable gain and `build:use-vbo=true` was 8% slower, which confirms the "harmful" comment. See [vao-fastpath/README.md](vao-fastpath/README.md).
- [x] **22. Gen9 `CC_VIEWPORT` re-emit in BLORP (#11647) (S). Measured; no change.** With reuse re-enabled, the formerly flaky multiview test passed 300 of 300, but that cannot rule out a sub-1% flake, and the saving is one 32-byte allocation per BLORP operation. The workaround stays. See [blorp-ccvp/README.md](blorp-ccvp/README.md).
- [x] **23. Barrier flush precision (M). Traced; no change.** A vkmark `INTEL_DEBUG=pc` trace (about 50,000 frames) shows about ten PIPE_CONTROLs per frame, all required by the PRM, by aux/hashing transitions or by the application's barriers. The only candidate is the first-`PIPELINE_SELECT` flush in each command buffer, worth +1–10% only at about 3,000 fps. It can't be dropped safely, because the previous command buffer's pipeline mode is unknown at record time. See [barrier-precision/README.md](barrier-precision/README.md).
- [x] **24. VF cache across secondary command buffers (M). Done, and it found an upstream bug.** A Gfx9 VF cache invalidate was queued after the draw that needed it, so a draw from a buffer 4 GiB away from the previous one read stale vertices: 50/50 failures, including on installed Mesa 26.0.8. Fixed by invalidating before the vertex buffers are emitted. Secondaries are now tracked on entry and exit instead of always invalidating: 2,000 → 2 invalidates per 1,000 executions, with no GPU time change in that benchmark. See [vf-secondary/README.md](vf-secondary/README.md).
- [x] **25. Pipeline-statistics query flush (S). Investigated; no change.** Every statistics counter is incremented by in-flight work and read with `MI_STORE_REGISTER_MEM`, so the CS stall at begin and end is what makes the result exact. None of the stats can skip it.

Compiler (brw on Gfx9):
- [x] **28. Spill single GRFs instead of whole VGRFs (M). Already done upstream.** `spill_reg()` fills and spills only the accessed range (`calculate_unspill_ranges()`). The stale comment that said otherwise is fixed. See [compiler-gfx9/README.md](compiler-gfx9/README.md).
- [x] **29. Keep SIMD16 for 32-bit quad swizzles and mixed-mode float (M). Investigated; nothing to gain.** Both limits split a single instruction, not the whole shader. Every legal alternative needs as many instructions or more, and the mixed-mode caps are PRM rules.
- [x] **30. Allow the safe subset of MAD → MAC fusion on Gfx9 (M). Already done.** Gfx9 three-source operands have no register-file field, so MAD can never read the accumulator. MAD → MAC is the only legal fusion, and `brw_opt_mac` already emits it (`mul acc0` followed by `mac`s).
- [x] **31. Remove the unneeded byte → word expansion in int8 DPAS emulation (S). Measured; keep it.** Removing it is correct but 11% slower (16.5 vs 18.5 GMAC/s). Also widening src1 is 31% slower. The FINISHME now records this. See [dpas-int8/README.md](dpas-int8/README.md).
- [x] **32. Calibrate the Gfx9 cost model from HD 620 measurements (M). Done.**
  - *Latency:* measured with dependent chains with the clock pinned at 1 GHz. 32/64-bit ALU, MAD, integer multiply and most math are within about 2 cycles of the model. EXP2/LOG2 were 4 cycles slow and now have their own Gfx9 entry.
  - *SIMD32 choice:* unchanged across 14 glmark2 scenes. Nearly every SIMD16/SIMD32 pair scores as a tie under the render-target-write cost. Forcing SIMD32 ranges from +7.5% to −5% (about +0.8% on average), and the model cannot tell those shaders apart, so the decision rule stays.

Power:
- [x] **40. RPS down-clock timeout and RC6 media power-gate hysteresis (M). Done: an opt-in profile.**
  - *RPS:* thresholds of 70/40 instead of 50/30 cut GPU power by 3–10% on paced loads. Light frames take 7% longer, and sustained load is unchanged.
  - *RC6:* a power-gate hysteresis of 60 instead of 250 saves about 5% more. Cross-context synchronised submissions get up to 7% slower.
  - Because both knobs trade latency for power, `hd620-power-profile save|default` and a boot/resume unit are installed with `default` selected. See [power-rps/README.md](power-rps/README.md).
