# Hardware paths missing from an API or disabled on the HD 620

Scope is the Intel Kaby Lake GT2 at PCI ID `8086:5916`, running i915 on Linux `7.0.0-43-generic`. The installed ANV is Mesa 26.0.8, and the two comparison ANV builds use checkout `0e9e1086bb86`. Intel iHD 26.1.2 is the VA-API reference. “Exposed” is evaluated per API, driver build, mode and profile. This inventory covers the evidenced paths and labels where hardware support is inferred or where the implementation still needs proof. ### HEVC decode fallback design

The Mesa 26.0.8 release source maps the input buffer, parses HEVC headers on the CPU, and emits HCP slice, reference, weight and bitstream-object commands directly. The checkout instead produces its slice commands through HuC. That identifies the code to compare. The older mapping and timing assumptions need special review before reusing the fallback. In particular, a command-recording-time read cannot observe bitstream writes that occur later on the GPU. A conformant fallback must respect supported memory types and the submitted ordering of uploads, barriers, and decode. Test a bitstream produced by a preceding GPU copy. If the old route cannot meet that ordering, consider queue-ordered slice preparation or use the HuC path for the public capability. Keep the older installed-driver result scoped to the proven clips. [Mesa 26.0.8 decoder source](https://gitlab.freedesktop.org/mesa/mesa/-/raw/mesa-26.0.8/src/intel/vulkan/genX_cmd_video.c) · [Saved slice preparation](evidence/hardware-paths/mesa-26.0.8-video.c#L669) · [Fresh i915 firmware query](evidence/hardware-paths/i915-current.txt)

## Keep in the existing API or leave as research

| Path | Recommendation |
| --- | --- |
| **VP8, MPEG-2 and baseline JPEG encode/decode and VC-1 decode** | The tested VA-API hardware-assisted VP8, MPEG-2 and JPEG paths already work. VC-1 decode was advertised only. The checked Vulkan codec registry has operations for H.264, HEVC and AV1 encode/decode and VP9 decode. These older codecs have no standardized Vulkan Video operations in that registry. Keep the VA-API paths. A Vulkan implementation would need a new codec API contract and a consuming application as well as driver work. [VA-API work](evidence/media-smoke.txt) · [Codec enums](../mesa/include/vulkan/vulkan_core.h#L9230) · [Khronos registry](https://registry.khronos.org/vulkan/) |
| **VP9 encode on Kaby Lake** | The archived i965 project records a historical hardware-assisted route, and an Intel contributor describes incomplete Gen9 VP9 features. Neither installed VA driver advertises VP9 encode on this machine. Vulkan also has no VP9 encode operation in the checked registry. Treat this as a historical or partial path. Reproduce it on the actual GPU and compare features, quality and throughput against software before contemplating an experimental VA path. [Archived i965 driver](https://github.com/intel/intel-vaapi-driver/blob/master/README) · [Intel implementation discussion](https://github.com/intel/media-driver/issues/630) · [Local i965 inventory](evidence/va-i965.txt) |
| **Flexible encode controls and video stats** | iHD exposes H.264/HEVC FEI entry points and a stats entry point. These are exposure observations, with the exact hardware contribution and user benefit untested. Leave them with iHD unless a consumer needs a particular control. Read back the intended stats or control effect before selecting a Vulkan equivalent. [Local VA entry points](evidence/va-iHD.txt) |
| **VA-API ICQ, QVBR and AVBR** | The VA encode debug logs advertise ICQ and QVBR for the tested H.264 and HEVC configurations and AVBR for H.264. This probe exercised only CQP, CBR and VBR. The Vulkan rate-control API has default, disabled, CBR and VBR modes. Leave these other policies in iHD unless there is a defined API mapping and a verified workload. [iHD H.264 query](evidence/hardware-paths/h264_vaapi-high-CBR.log) · [iHD HEVC query](evidence/hardware-paths/hevc_vaapi-main10-VBR.log) · [Vulkan rate-control enums](../mesa/include/vulkan/vulkan_core.h#L12167) |
| **FP32 atomic add and cooperative matrices** | The chipset has shader resources, and the checkout has modes that can implement some features in software on those resources. For atomics, prove compare-exchange lowering for each memory class, ordering, NaNs and contention. For matrices, compare verified results and throughput against tuned ordinary shaders before enabling the opt-in path by default. ## Reproduction and order of work

Run [the installed Vulkan HEVC parity probe](hevc-vulkan-check.sh) and [the rate-control and scaling probe](media-paths.py) to reproduce the fresh tests. The scaling probe reports the largest sampled process counters. Engines can overlap, so the values do not represent elapsed playback time. The HEVC parity probes pin the installed ICD and check the renderer and Vulkan decoder selection. No boot changes or new driver implementation were required for this investigation.

1. For a Vulkan codec project, recover the working HEVC decode path. Compare source and confirm which parts of the installed implementation can be reused.
2. For a driver performance project, pursue multi-mip HiZ. It is the only new low-level optimization here with a large measured benchmark effect.
3. For an app-facing media project, use VA-API hardware capabilities and bench direct interop. Implement Vulkan HEVC encoding or rate control when that API is an actual requirement.
4. For copy or profiling work, obtain effective engine comparison or authorized counter evidence before expanding public API support.
